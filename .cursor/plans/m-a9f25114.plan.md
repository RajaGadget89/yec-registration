# MCP RAG Vector-first One-shot

## Goal

Minimize latency and LLM tokens while keeping MCP secure and governed by MCP Management. Ship a vector-first retrieval pipeline and targeted APIs in one release.

## Design Summary

- Vector-first search with Supabase Postgres + pgvector (no new vendor).
- Parameterized, minimal-payload MCP endpoints. Default to small field sets; expand via fields param.
- Keep MCP Management: use registry for enabled types, rate limit, audit, cache, API-key auth.
- Background embedding upsert on CMS changes + full reindex job.

## New/Updated Endpoints

- GET `app/api/mcp/public/search/route.ts`
- Body (POST accepted too): { q, language?, types?, topK?=5 }
- Returns: [{ type, id, score, highlights }]
- Respects registry, rate limit, audit, cache.
- GET `app/api/cms/[type]/route.ts` (augment)
- New params: `ids` (comma-separated), `fields` (allowlist), `limit`, `page`.
- Default fields:
  - faq: id,title,description,url
  - news: id,headline,excerpt,url,image_url,published_at
  - activities: id,title,summary,url,image_url,scheduled_at
  - pages: id,title,slug,url
- GET `app/api/mcp/public/comprehensive/route.ts`
- Keep; supports `types` (already added). Document for bulk/export only.

## Data Model (Supabase)

- Table `cms_embeddings` (pgvector)
- id (uuid), type (text), item_id (uuid), language (text), chunk_id (int), content (text), embedding vector(384), published_at (timestamptz), is_active (bool), updated_at (timestamptz)
- Indexes: (type,item_id), ivfflat on embedding.
- SQL migration: create extension if not exists vector; table + indexes.

## Embedding Pipeline

- Server job `scripts/embed-cms.ts` (node) or API admin route
- Upsert on publish/update/unpublish for cms_faq_items, cms_activity_cards, cms_news, cms_pages.
- Chunk long HTML to plain text (e.g., 800-1200 tokens) before embedding.
- Store per-chunk rows in `cms_embeddings`.
- Full reindex command for recovery.

## Search Algorithm

1) Normalize query (strip HTML, lowercase, language detect optional).
2) Vector search per requested types: cosine topK per language.
3) Return minimal hit payload with `{type,id,score,highlights}`.
4) Client follows up with `/api/cms/[type]?ids=...&fields=...` to fetch display data.

## Security & Governance

- Validate API key via existing `validateMCPApiKey`.
- Use `mcpContentRegistry` to filter enabled types.
- Rate limit per key type; audit via `auditMCPAccess`.
- Sanitize HTML; enforce `fields` allowlist.
- Cache: 60s TTL with ETag; respect `types,language,q,topK` in cache key.

## n8n MCP Client Contract

- Tool: MCP_Search
- Params: q, types[], language, topK (5)
- Tool: MCP_Fetch
- Params: type, ids[], fields (comma), language
- Agent Prompting
- Infer intent → call MCP_Search → MCP_Fetch with minimal fields; expand only if needed.

## Rollout Steps

1) SQL migration: enable pgvector; create `cms_embeddings` + indexes.
2) Implement `search` endpoint (vector path) and keyword fallback if embeddings empty.
3) Augment CMS endpoints with `ids` and `fields`.
4) Implement embedding upsert job and a one-time full reindex.
5) Update n8n MCP Client nodes (tools + params); adjust Agent prompt.
6) Perf + token tests; tune topK and default fields.

## Risks/Mitigations

- Large HTML: chunking + strip HTML.
- Cold index: keyword fallback; warmup job.
- Token costs for embeddings: batch, cache, and only re-embed changed items.

## Acceptance Criteria

- 95th percentile latency reduced (>50%) vs comprehensive for typical Q&A.
- Token usage per answer reduced (>60%).
- Security: rate-limit/audit present; only enabled types returned.
- n8n workflow fetches <= topK minimal items by default.
